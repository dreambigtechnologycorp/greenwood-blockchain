# Seven-node RPC proxy, DNS and certificate handoff

Status: prepared configuration, not activated. Run credential commands yourself,
outside AI. Existing production keys are not regenerated by this procedure.
The HTTPS-upstream support accompanying this document must be reviewed and included
in a new pinned release before deployment; release 1d8a0bd does not contain it.

## Intended path

| DNS name | Private LAN address | HTTPS port | Backend |
| --- | --- | --- | --- |
| rpc-node-1.greenwoodblockchain.com | 192.168.72.100 | 8443 | http://127.0.0.1:9201 |
| rpc-node-2.greenwoodblockchain.com | 192.168.72.101 | 8443 | http://127.0.0.1:9201 |
| rpc-node-3.greenwoodblockchain.com | 192.168.72.102 | 8443 | http://127.0.0.1:9201 |
| rpc-node-5.greenwoodblockchain.com | 192.168.72.104 | 8443 | https://rpc-node-1.greenwoodblockchain.com:8443 |

Providers 6–7 use https://rpc-node-1.greenwoodblockchain.com:8443 directly.
Node-5 is a fixed upstream relay, not a fourth validator or independent consensus
witness. It has no automatic failover. Its responses originate from node-1.
The genesis HTTP consensus endpoints on port 9201 remain unchanged.
Registry DNS remains registry.greenwoodblockchain.com; its separate TLS/issuer
configuration is not replaced by these RPC settings.

The frontend terminates TLS, then verifies the upstream CA, hostname and expiry.
The same explicitly pinned CA certificate trusts these RPC endpoints. Use one
approved RPC issuing CA for this composition. TLS does not authenticate customers;
keep RPC listeners reachable only from the approved LAN/VPN until a separately
reviewed public-access policy exists. Do not expose validator consensus/operator
interfaces through a public tunnel merely to make the RPC checks succeed.

## 1. Prepare Cloudflare DNS and cloudflared ingress

Reuse your existing tunnel and its management method. Do not create a replacement
connector, overwrite its full configuration or expose its credentials to AI.
Public RPC URLs use ordinary HTTPS port 443, for example
`https://rpc-node-5.greenwoodblockchain.com`. Port 8443 belongs to the LAN origin.

For a locally managed tunnel, merge the prepared `cloudflared-rpc.ingress.yml`
rules before the existing final catch-all. Keep all existing SSH, registry and
application routes and the tunnel/credentials settings unchanged. Each route uses
a LAN IP service URL, `originServerName` matching the certificate, a public CA
`caPool` file on the connector, and `noTLSVerify: false`. Never point a tunnel's
service URL back at its own public hostname. For a remotely managed tunnel, enter
the equivalent hostname, HTTPS service URL and origin parameters in the dashboard;
editing a local config is not a replacement for dashboard-managed routes.

Example rule (the complete prepared fragment has all four nodes):

```yaml
- hostname: rpc-node-5.greenwoodblockchain.com
  service: https://192.168.72.104:8443
  originRequest:
    originServerName: rpc-node-5.greenwoodblockchain.com
    caPool: /etc/cloudflared/rpc-ca.pem
    noTLSVerify: false
```

The connector needs only the public CA file, not the RPC or CA private keys.
Before publication, establish the intended Cloudflare Access/network policy.
A working tunnel is not authorization to expose every RPC method publicly.
Browser login policies are unsuitable for unattended provider calls unless those
clients explicitly support the required credentials. Internal provider calls below
avoid this dependency; do not bypass Access to make a test pass.

In Cloudflare DNS, route each of the four RPC hostnames to your existing tunnel's
`<UUID>.cfargotunnel.com` CNAME, preserving existing unrelated records. The tunnel
dashboard can create these records. For locally managed tunnels the operator may
instead run, after reviewing the exact existing tunnel:

```sh
cloudflared tunnel route dns EXISTING_TUNNEL_NAME rpc-node-1.greenwoodblockchain.com
cloudflared tunnel route dns EXISTING_TUNNEL_NAME rpc-node-2.greenwoodblockchain.com
cloudflared tunnel route dns EXISTING_TUNNEL_NAME rpc-node-3.greenwoodblockchain.com
cloudflared tunnel route dns EXISTING_TUNNEL_NAME rpc-node-5.greenwoodblockchain.com
cloudflared tunnel --config /PATH/TO/YOUR/CONFIG.yml ingress validate
cloudflared tunnel --config /PATH/TO/YOUR/CONFIG.yml ingress rule https://rpc-node-5.greenwoodblockchain.com
```

These are operator-only steps: DNS publication and applying the tunnel config are
live changes. Apply only in your approved window after origin TLS tests pass.
No tunnel reload/restart is performed during this preparation.

### Internal upstream resolution

Node-5's Apache relay and providers 6–7 use the direct LAN HTTPS upstream on 8443,
not Cloudflare's public edge. On those three nodes, use your existing private
resolver or a narrowly scoped `/etc/hosts` entry:

```text
192.168.72.100 rpc-node-1.greenwoodblockchain.com
```

This preserves hostname verification while keeping traffic inside the LAN. Check
`getent ahostsv4 rpc-node-1.greenwoodblockchain.com` there before startup. Do not
redirect Cloudflare service URLs to public DNS or send the internal :8443 upstream
through an Access login page. Node-4 dnsmasq changes are optional; no networkd or
NFS restart is needed. Public clients continue to use Cloudflare and port 443.

References: [Cloudflare routing](https://developers.cloudflare.com/tunnel/concepts/routing/),
[HTTPS origin verification](https://developers.cloudflare.com/tunnel/troubleshooting/https-origins/),
[origin parameters](https://developers.cloudflare.com/tunnel/reference/origin-parameters/).

## 2. Request the four RPC certificates yourself

Use your established offline CA/custody workflow. Reuse a suitable existing RPC
TLS key/CSR when present; never reuse validator, provider, governance, registry
issuer or SFTP keys as TLS keys. Do not bring CA private keys onto cluster nodes.
A registry-only certificate does not cover the RPC names.

For each node 1,2,3,5, set the exact DNS name and create a CSR using that node's
existing TLS private key (paths below are operator placeholders):

```sh
umask 077
rpc_name=rpc-node-1.greenwoodblockchain.com
openssl req -new -key /PRIVATE/node-1-rpc.key \
  -subj "/CN=$rpc_name" -addext "subjectAltName=DNS:$rpc_name" \
  -out node-1-rpc.csr.pem
openssl req -in node-1-rpc.csr.pem -noout -verify -text
```

If a dedicated RPC TLS key does not exist, YOU may create it on your offline
custody system first, using a new filename and your existing backup procedure:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 \
  -out /PRIVATE/node-1-rpc.key
chmod 600 /PRIVATE/node-1-rpc.key
```

Never overwrite an existing key. Repeat with separate keys and exact names for
nodes 2,3,5. Submit only the CSRs to your approved CA. Request DNS SAN equal to the
exact hostname, CA:false, serverAuth EKU and suitable signing/key-encipherment
usage. Have the issuer enforce these extensions; do not blindly copy arbitrary
CSR extensions. Obtain the leaf certificate, intermediates if needed and the
approved CA certificate. With an intermediate CA, use a fullchain server file and
supply the required intermediate chain when independently verifying it.

Offline public certificate checks (directly issued leaf example):

```sh
openssl verify -CAfile rpc-ca.pem -purpose sslserver \
  -verify_hostname rpc-node-1.greenwoodblockchain.com node-1-rpc.crt.pem
openssl x509 -in node-1-rpc.crt.pem -noout -dates -ext subjectAltName
openssl x509 -in rpc-ca.pem -noout -fingerprint -sha256
```

For the inventory `ca_sha256`, remove colons and lowercase the certificate
fingerprint. This is the certificate DER fingerprint, NOT `sha256sum rpc-ca.pem`.
You alone check each certificate/private-key match and maintain backups.

## 3. Complete the prepared inventory

The local preparation directory contains `rpc-frontends.pending.yml` and
`cloudflared-rpc.ingress.yml`. The overlay contains no secrets; private_key values
are future target paths, not files opened by the assistant. Replace
REPLACE_RPC_CA_DER_SHA256 with the verified fingerprint. Keep the source revision
blocked until the proxy changes are merged and a replacement release is built.
Preserve any existing registry/controller HTTPS entries when combining lists:
Ansible list variables replace, rather than append to, earlier lists.

Operator-provision each host's certificate and private key at the listed paths,
with root-owned non-writable ancestry and private key mode 0600. Provision only
that host's key; put the public CA certificate on all RPC/provider clients.
The existing control-plane role checks ownership, key pairing, CA fingerprint,
chain, expiry and hostname. Those checks read private keys and therefore remain
operator-only, including in check mode. Use the established protected file inputs.

## 4. Reviewed installer startup order

Local `--syntax-check` does not inspect credentials or activate services.
The corrected fresh installer stages all runtime, application-hosting and
control-plane configuration before starting the validators. It then starts and
checks validator HTTPS origins, starts and checks non-validator RPC relays,
installs the pinned public RPC CA into provider-only system trust, checks each
provider endpoint's chain/genesis/finality and finally starts providers.
Registry, policy consumers and other hosting endpoints follow in their existing
explicit activation phase. The origin checks use curl --resolve with CA/hostname
verification, so public Cloudflare publication is not a bootstrap dependency.

Set `greenwood_rpc_ca_src` to the operator's public RPC CA PEM file and
`greenwood_rpc_ca_file_sha256` to its `sha256sum`. This PEM-file checksum is
separate from the frontend's CA DER fingerprint. The installer verifies the file
before mutation, installs it into provider-only system trust and refreshes trust
when changed. This does not provision CA private keys.

Before running installation, complete DNS/hosts resolution on nodes 5–7, issued
certificates and the complete protected control-plane input set. The installer
rejects validator proxy cycles and provider-only endpoints outside the declared
direct validator HTTPS origins. Keep all approvals false until you personally
approve installation. Do not use check mode to run secret-bearing roles or bypass
preflight errors. Fresh installation refuses an already initialized chain.

No service starts occur during preparation/testing. The operator runs the actual
fresh installer only after its reviewed approvals and inputs are complete.

## 5. Verify after your authorized activation

From node-5 and nodes 6–7, verify the direct upstream with the public CA and internal name resolution:

```sh
curl --fail --cacert /etc/greenwood/tls/rpc-ca.pem \
  https://rpc-node-1.greenwoodblockchain.com:8443/v1/chain/status
curl --fail --cacert /etc/greenwood/tls/rpc-ca.pem \
  --resolve rpc-node-5.greenwoodblockchain.com:8443:192.168.72.104 \
  https://rpc-node-5.greenwoodblockchain.com:8443/v1/chain/status
```

After authorized Cloudflare publication, separately test the public URL without
`:8443`, using normal system trust for Cloudflare's edge certificate and the
approved access policy. Do not use the private origin CA as a substitute for
public edge verification. Cloudflare edge and RPC origin certificates are separate.

Check chain ID greenwood-prod-v1 and genesis hash
3599962055a045d9e34c357cfd69f177488f96004606108228d61938071493ed.
Confirm advancing finalized heights and the expected public validators. Test
wrong-name/untrusted/expired upstream certificates in disposable acceptance
fixtures; the relay must fail closed. Never use curl -k or disable peer checking.
Bring back only DNS results, certificates/CSRs, CA public certificate, fingerprints
and redacted checks. Never share private keys, vaults, passwords or tokens.
